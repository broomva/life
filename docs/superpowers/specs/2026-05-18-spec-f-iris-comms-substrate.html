§0 Preamble

§0.1 Naming — Iris, the messenger goddess

Iris (Ἶρις, Îris) is named for the Greek messenger goddess — the rainbow-bridge between Olympus and the mortal realms, charged with one duty: carry the message faithfully, whatever its origin or destination. She is the single-purpose messenger, distinct from Hermes who carries many roles (commerce, thieves, psychopomp, herald). This naming intentionally contrasts the workspace’s existing hermes tooling, which is polymorphic; Iris is one trait, many adapters, no role creep.

§0.2 Disambiguation — this is not Fisher’s iris dataset

Disambiguation

The Iris in this spec refers exclusively to the Greek messenger goddess. It is unrelated to the Fisher iris flower dataset from statistical learning literature, the anatomical iris of the eye, the iris-rs ML crate, NASA Iris satellite missions, JetBrains Iris, the Iris messaging library (Java), or any other prior software-engineering use of the name.

When the substrate is referenced in code, prose, docs, or commit messages, the form "Iris (the Life messaging substrate)" or just Iris in context is preferred. The lowercase identifier iris is used uniformly for crate names, daemon binaries (irisd), proto paths, lifegw routes, and policy gates.

§0.4 Scope sentence

Iris is the multi-channel messaging substrate of the Life Agent OS. It bridges WhatsApp (Web automation and Cloud API), Telegram, Signal, Slack, Discord, Matrix, iMessage, SMS via Twilio, and Web (in-app chat) — in both directions — to the canonical Life agent loop. It owns one trait (ChannelConnector), one canonical Message / ConversationRef / ParticipantRef schema, a single daemon (irisd), and a lifegw edge surface that mirrors lifed’s session-stream contract. Identity is bootstrapped through Anima (Spec D); compute is dispatched through Inference (Spec E); durability is via Lago; observability via Vigil; billing via Haima; timers via Chronos.

§1 Why — The Substrate Gap

§1.1 Current state — ad-hoc Twilio across the workspace

Messaging integrations across the Broomva workspace have grown organically and incoherently. As of 2026-05-18, the same ground — "let an agent read inbound messages and send outbound replies on channel X" — is re-implemented in at least five places:

  • Exclusive Rentals (Life Module tenant). A bespoke Twilio Programmable SMS webhook handler in freelance/exclusive-rentals/ forwards SMS into arcand via an HTTP relay; each tenant configures its own Twilio account, signing secrets, and message-status polling logic.
  • Stimulus (work). A WhatsApp Cloud API webhook handler that posts to a custom internal queue; identity binding is by phone-number string lookup; no rotation handling.
  • Hakip (habit assistant). A Telegram bot via teloxide embedded directly in the app binary; deployment lifecycle is coupled to the app’s release schedule.
  • Sentinel (freelance). A Twilio Conversations integration with its own per-tenant identity map and per-conversation lock that reimplements roughly half of the canonical pattern.
  • chatOS web. An in-app WebSocket channel that has semantics very similar to the others but no shared schema, no shared trust model, and no integration with Anima or Lago.

Each integration carries the same ten or so failure modes: HMAC signature verification done inconsistently or skipped, per-conversation ordering not enforced, the WhatsApp 24-hour customer-care window not tracked, identity binding ad-hoc and unrotatable, observability mostly absent, no per-channel capability negotiation (e.g. markdown formatting fallback differs by channel), no central rate-limiting, no policy gate, and no billing tie-in for outbound messages that may incur per-message costs.

Five tenants on the authored-agents deployment plan need at least three channels each (typically WhatsApp + SMS + web). That implies fifteen near-duplicate integrations within twelve weeks if nothing changes; that is the substrate gap.

§1.2 The three structural costs (mirror of Spec E’s framing)

Spec E framed the inference gap as three structural costs (no silicon fan-out, no agent-loop primitives, no Lago/Anima integration). The messaging gap has the same shape:

  1. No channel fan-out. Each new channel (Signal CLI, Matrix appservice, iMessage via a Mac mini bridge) requires a one-off integration with no shared inbound/outbound shape. Adding the sixth channel costs as much as adding the first.
  2. No agent-loop primitives. Per-conversation serialization, identity unification across handles, capability-typed degradation (markdown → plaintext on SMS), and re-engagement window timers (WhatsApp 24h) have no schema or trait surface; they are re-implemented — usually wrong — per integration. Bot-Framework and Twilio Conversations had to solve these in proprietary code; libpurple has done it since 1998 as prpl plugins.
  3. No Anima / Inference / Lago / Vigil integration. Messages today don’t carry the agent’s DID, aren’t Lago-content-addressed, aren’t Vigil-instrumented, aren’t Inference-routed (which model handles which channel?), aren’t identity-bound (a phone number swap is a manual database surgery), and have no billing surface. Every other Life substrate is event-sourced and identity-scoped; messaging is the substrate that escapes the contract.

§1.3 Why now

Three triggers converge on 2026-05-18 to make this the right moment:

  • Anima Spec D is 100% shipped with six custody backends. Iris can bootstrap identity from a phone number to an EcdsaP256Identity without needing to design custody itself.
  • Inference Spec E foundation (E-Sub-A) shipped. Per-channel, per-session compute routing is a real handle Iris can consume rather than a future hope.
  • Five tenant deployments needing channels are queued. The cost of not having Iris is now scoped, dated, and quantified.

§2 Prior-Art Convergence — The Eight Invariants

Iris is not a green-field design. Five large, long-lived messaging substrates converge on the same set of invariants from independent starting points. The Iris trait surface is the intersection of their lessons, with a small number of deliberate departures motivated by the Anima / Inference substrate-cluster pattern.

§2.1 The five reference systems

libpurple (Pidgin, 1998 — present)

The longest-running multi-protocol messaging substrate in production. Defines the prpl (PRotocol PLugin) ABI: a per-protocol dynamic-library contract over a canonical account / buddy / conversation / IM-message model. libpurple shipped ~25 protocols at peak; modern Pidgin still supports XMPP, IRC, SIP, Matrix, and (historically) AIM, ICQ, MSN, Yahoo, Bonjour, Gadu-Gadu, Zephyr. The plugin daemon pattern is the canonical alternative to compiled-in adapters (see L6-D8).

Convergent lessons: (a) canonical message + conversation + participant schema is essential; (b) per-protocol plugin trait, not per-protocol inheritance, scales to twenty-plus channels; (c) per-conversation serialization is so universal it became part of the core abstraction; (d) "presence" is a separate axis from "message" and deserves its own trait (deferred to Phase 2 — see §11). Cautionary lesson: plugin overload — libpurple’s peak of ~25 protocols was largely community-contributed plugins with highly variable quality, security, and conformance; the maintenance load eventually fragmented the project. Iris mitigates by gating with a conformance battery (F-Sub-G) and requiring compiled-in Rust crates in v1 (L6-D8).

Matrix mautrix — bridgev2 NetworkConnector (2024+)

The current state-of-the-art for federation-bridge design. Defines NetworkConnector as the per-protocol trait, with bridgev2 (the bridge framework) handling room/conversation lifecycle, identity portal-puppeting (a remote-network user appears as a Matrix user under bridge control), and end-to-bridge encryption. The mautrix bridges for WhatsApp, Telegram, Signal, Discord, Slack, and iMessage all implement NetworkConnector and share identical handling for room creation, user portaling, and message reconciliation.

Convergent lessons: (a) a NetworkConnector-style trait with a few methods (send, receive, handle_event, capability declarations) is sufficient for the messaging side and forces discipline; (b) the bridge frameworks centralise rate-limiting, retry, and identity unification so per-channel impls stay small; (c) puppeting (one side acts as the other identity) is one of three distinct trust regimes — the others are relay and proxy — and the trait shape must let the bridge declare which it implements (see TrustMode). Iris adopts this terminology and trait shape almost directly.

Microsoft Bot Framework — BotAdapter + Activity (2016+)

The most schema-disciplined messaging contract in the industry. Defines Activity as the canonical message envelope (id, type, from, conversation, recipient, text, attachments, channelId, …) and BotAdapter as the per-channel translation layer. Channels covered include Microsoft Teams, Skype, Slack, Facebook Messenger, Twilio SMS, Webex, Direct Line, Web Chat, LINE, and Telegram.

Convergent lesson: the canonical schema must be channel-agnostic, with capability declarations and graceful degradation tracking. Bot Framework enforces channel data passthrough — channel-specific fields travel in a typed channelData envelope so the canonical schema doesn’t bloat. Iris adopts this pattern as Message::channel_data: Option<serde_json::Value>. Cautionary lesson: schema drift across channel versions — the framework has accumulated ~7 schema versions across a decade; new channels arrive and old ones evolve. A conformance battery is mandatory.

Twilio Conversations API (2020+)

The clearest commercial framing of the multi-channel problem. Conversation, Participant, and ProxyAddress are the three primitive types; a single Conversation can have participants on SMS, WhatsApp, MMS, web chat, Facebook Messenger, and others, each represented by a Participant bound to a ProxyAddress (the Iris-side handle). The substrate guarantees per-conversation message ordering and bridges identities across channels via ProjectedAddress.

Convergent lessons: (a) the canonical identity is the Conversation, not the channel-native conversation id; (b) per-channel handles are owned by the substrate (the ProxyAddress — e.g. a phone number you provisioned) so identity binding survives channel-side reassignments; (c) per-conversation ordering is non-negotiable and must be enforced by the substrate.

OpenClaw — 40+ channel relay (2025-2026, broomva)

OpenClaw is the workspace’s most aggressive experiment in cross-channel routing. It runs forty-plus adapters (WhatsApp Web via OpenWA, Telegram via teloxide, Signal via signal-cli, Slack via slack-rs, Discord via serenity, Matrix via matrix-rust-sdk, iMessage via a Mac-mini bridge, X DMs via headless browser, IG DMs via similar, plus many smaller adapters) behind a seven-stage processing loop: ingress → decode → canonicalise → identity-resolve → queue → agent-dispatch → outbound. Each session (loosely a conversation) holds a per-session command queue that serializes inbound → agent → outbound order.

Convergent lessons (and unique additions Iris inherits): (a) the seven-stage loop is the right pattern for inbound, but is too deep at v1 — Iris collapses it to a four-stage loop (decode → canonicalise → serialize → dispatch) and lets Lago / Praxis / Inference own the rest; (b) the per-session command queue maps cleanly onto a tokio::Mutex keyed by ConversationRef; (c) OpenClaw demonstrates that compiled-in Rust crates can scale to ~40 channels if (and only if) per-channel SDK churn is firewalled by a stable canonical schema; (d) the operational pain points OpenClaw discovered — webhook auth sprawl, SMS-spoofing risks, capability degradation done in code instead of declaratively — map directly to the L6-D2…L6-D7 decisions below.

§2.2 The eight convergent invariants

Distilling the five systems above — spanning 1998 (libpurple) through 2026 (OpenClaw) — produces a set of eight invariants that every multi-channel messaging substrate ends up satisfying, by accident or design. Iris satisfies all eight by construction.

# Invariant Why it is non-negotiable Iris artifact
I-1 Canonical message schema — channel-agnostic envelope, channel-specific payload travels in a typed side-channel. Bot Framework Activity. libpurple PurpleMessage. Without it, every agent has to know every channel’s quirks; with it, agents are channel-blind. iris-core::Message
I-2 Per-protocol Connector trait — not inheritance, not switch-on-channel-id. libpurple prpl. mautrix NetworkConnector. Bot Framework BotAdapter. The trait surface is small (≤10 methods); the implementation is the channel-specific work. iris-core::ChannelConnector
I-3 Per-conversation serialization — messages within a single conversation must be delivered to the agent loop in order. Twilio Conversations enforces it. OpenClaw discovered it the hard way (out-of-order messages produced incoherent agent responses). All five systems converge on this. Per-ConversationRef tokio::Mutex in irisd
I-4 Identity unification layer — a single agent identity spans WhatsApp phone, Telegram handle, Slack user, Discord snowflake. Bot Framework projects via Activity.from.id; Twilio via ProjectedAddress; mautrix via portal-puppeting. Without it, the agent sees the same human as five different users. iris-core::Participant + Anima DID binding (L6-D4)
I-5 Symmetric bidirectional pipelines — inbound and outbound use the same trait, the same schema, the same observability points. Bot Framework BotAdapter handles both via the same Activity. libpurple prpl too. Asymmetry has historically been the source of "outbound works fine, inbound silently drops at 5% rate" bugs. ChannelConnector::send + ChannelConnector::receive
I-6 Capability-aware degradation — rich content (markdown, attachments, quote-reply, threads) declared per-channel; substrate gracefully degrades when target channel lacks support. SMS doesn’t do markdown; Telegram doesn’t do iMessage tapbacks; Slack threads aren’t WhatsApp quote-replies. Without typed capabilities, agents emit content the channel silently strips. iris-core::ChannelCapabilities + DegradationPolicy
I-7 Webhook + WS dual ingress — both push (HTTP webhook callbacks) and pull / stream (WebSocket, long-poll, gRPC streaming) must be first-class. WhatsApp Cloud API is webhook-only; OpenWA is WS-only; Telegram supports both; Twilio is webhook-primary with streaming for Conversations. The substrate must handle both shapes uniformly. lifegw routes POST /v1/iris/inbound + WS /v1/iris/stream
I-8 Trust-regime declaration — puppeting / relay / proxy — the bridge tells the world which identity model it uses. mautrix names these explicitly. Puppeting (remote user appears as local user under bridge control) has different consent semantics from relay (bridge speaks on behalf of users) and proxy (bridge mediates without claiming identity). Conflating them is the source of every "the bot said something I didn’t say" incident. iris-core::TrustMode + per-channel default in capabilities()
The eight convergent invariants. All five reference systems satisfy at least six; mautrix is the only one satisfying all eight.

The pattern in one sentence

A canonical message envelope, a per-protocol trait with a small surface, a per-conversation lock, a typed capability declaration, and a typed trust-mode declaration — produce a substrate that scales to dozens of channels without losing coherence. The eight invariants are different angles on this single sentence.

§3 Locked Decisions (L6-D1 – L6-D8)

Eight decisions are locked at draft-v0.1; further decisions may be added as sub-phases land. Numbering follows the L<layer>-D<n> convention — L4 is Anima (Spec D), L5 is Inference (Spec E), and L6 is the messaging layer covered by this spec. Each decision is paired with the rejected alternative to document the reasoning trail.

L6-D1 — crates/iris/ as a new substrate cluster

LOCKED Cluster placement

Iris lives in a new top-level workspace cluster core/life/crates/iris/, a sibling of crates/anima/, crates/inference/, crates/chronos/, crates/vigil/, and crates/haima/. Sub-crates: iris-core (trait + types), iris-proto (protobuf surfaces), iris-runtime (per-conversation lock + connector registry + Lago sink + Vigil instrumentation), iris-whatsapp-openwa, iris-whatsapp-cloud, iris-telegram, iris-signal, iris-slack, iris-discord, iris-matrix, iris-twilio, iris-imessage, iris-web, iris-conformance (cross-channel test battery). The daemon binary bin/irisd is sibling of haimad / lagod / arcand / anima-soma. The lifed proxy is crates/life-runtime/lifed-proxies/iris-proxy/.

Rejected: putting Iris in crates/life-relay/. life-relay is the agent-to-agent direct streaming crate (peer-to-peer RTT for collaborative work) and has a different threat model (mutually-authenticated agents) than Iris (one side is a human-or-channel-controlled identity). Conflating them is the source of the OpenClaw → relay confusion the workspace experienced in Q4 2025.

L6-D2 — Conversation event log is Lago-backed by default

LOCKED Lago is the durability substrate

Every inbound and outbound message is written to the Lago journal as a typed event in the iris.* namespace before the agent loop sees it (inbound) or before the channel receives it (outbound). Event kinds: iris.message_received, iris.message_sent, iris.message_failed, iris.conversation_opened, iris.conversation_closed, iris.participant_added, iris.participant_removed, iris.capability_degraded, iris.engagement_window_opened (WhatsApp 24h), iris.engagement_window_closed, iris.identity_bootstrapped. Each event carries the ConversationRef, the ParticipantRef, the ChannelId, the canonical Message, and the Anima DID of any agent identity involved.

Replay semantics follow Lago conventions: a conversation can be replayed to any point in time; an agent session can resume after a restart by rehydrating from iris.* events; lago replay --tree surfaces conversation history alongside the agent’s decision events (this is the Workflow-tick closure shape).

Rejected: per-channel native log (WhatsApp’s "messages history" REST endpoint, Twilio’s Message resource log). Each channel exposes a partial log with different retention, search, pricing, and access semantics. Treating them as authoritative produces five different "what did the agent say to user X yesterday?" answers. Iris’s Lago log is authoritative; channel-native logs are witnesses but not truth.

L6-D3 — Per-conversation serialization via tokio::Mutex

LOCKED One conversation, one writer at a time

irisd holds a DashMap<ConversationRef, Arc<tokio::Mutex<ConversationState>>>. Every inbound and outbound message handling path acquires the conversation’s lock before any agent dispatch, Lago write, or outbound channel call. The lock guarantees: (a) within a conversation, inbound message ordering is preserved end-to-end; (b) agent reactions do not race; (c) outbound writes within a conversation occur in the order the agent intended; (d) Lago journal writes within a conversation are strictly ordered.

The lock does not serialize across conversations — irisd handles N conversations in parallel limited only by tokio executor capacity. The lock is per-conversation, not per-channel, not global.

Lock acquisition timeout is bounded (default 30s) and surfaces as iris.message_failed { reason: "conversation_lock_timeout" } so an agent-loop deadlock cannot wedge a conversation indefinitely. Conversation locks are reaped after idle_lock_ttl (default 24h after last activity) by Chronos timers.

Rejected: per-conversation actor with its own tokio task. Conceptually clean but ~3× the memory per conversation (~50 KB per actor vs ~16 KB per Arc<Mutex<_>>) and complicates conversation-state migration on substrate restart. Five tenants × 50K conversations each × 50 KB ≈ 12.5 GB of idle actor state vs ≈ 4 GB locked-state which is feasible. The mutex pattern is also the one OpenClaw production-validated at ~40K concurrent conversations.

L6-D4 — Identity bootstrap via AnimaCustody DID derivation

LOCKED Phone / handle → DID via Anima

A first-time inbound message from a previously-unseen ParticipantRef (e.g. a new WhatsApp phone number) triggers identity bootstrap. The flow:

  1. iris-identity generates an ephemeral EcdsaP256Identity derived deterministically from (channel_id, participant_native_id, salt) using HKDF-SHA-256. The salt is a per-tenant secret in soma; rotation is supported by bumping a salt version.
  2. An iris.identity_bootstrapped { channel_id, participant_native_id, did, bootstrap_method: "ephemeral_hkdf" } event lands in Lago, becoming the authoritative binding.
  3. If the participant later upgrades — e.g. via a web app passkey-based WebCryptoAnima enrollment that proves ownership of the phone number — an anima.identity_rotated event chains the ephemeral DID to the new permanent DID (see Spec D L4-D10). The conversation history remains attributable to the same human across the rotation.
  4. For inbound channels that carry a verified identity claim natively (e.g. Slack workspace identity, Telegram user-id), iris-identity skips the ephemeral DID path and binds directly to the channel-native claim, attested by the channel’s webhook HMAC signature.

Iris does not own custody backends; it consumes Anima. The Arc<dyn AnimaCustody> used by irisd is the same one used by Arcan; bootstrap events go through Anima’s journal-replay semantics, not Iris-specific identity logic. This is the composition surface with Spec D.

Rejected: Iris-internal identity store, keyed by phone number. That would re-implement Anima in a parallel namespace and reproduce the SMS-spoofing risk surface (see §9 concern C-2) without the WebCryptoAnima passkey-upgrade path. Forcing the DID layer through Anima also unifies billing, observability, and audit across Iris and every other substrate.

L6-D5 — Tier-Service capability tokens for inbound adapters

LOCKED Webhook auth via lifegw Tier-Service caps

Every inbound webhook (Twilio HMAC, WhatsApp Cloud signature, Telegram header secret, Slack signing secret) is verified twice:

  1. Channel-native signature. The per-channel adapter verifies the inbound HTTP request using the channel’s native signature scheme (HMAC-SHA256 for Twilio and Slack, the WA Cloud X-Hub-Signature-256 for WhatsApp, Telegram’s X-Telegram-Bot-Api-Secret-Token header).
  2. Tier-Service capability token. The inbound route on lifegw (POST /v1/iris/inbound) requires a per-tenant Tier-Service capability token (mirror of Spec D’s Tier-User cap but service-scoped) signed by lifegw’s Tier-2 KMS key. The cap carries the channel_id scope, an audience aud="iris.inbound", and a 15-minute TTL (refreshed by a per-tenant agent process). Inbound requests without a valid Tier-Service cap are rejected with HTTP 401, before any channel-native signature check.

The defence in depth: a stolen Twilio HMAC secret alone is not sufficient to inject inbound messages — the attacker also needs to bypass the Tier-Service cap, which never sits in the channel webhook configuration. Conversely, a leaked Tier-Service cap allows replay only for its 15-minute lifetime and only against the scoped channel.

Outbound goes the other way: outbound calls from irisd to channels are guarded by per-channel iris.<channel>.outbound.* policy gates in .control/policy.yaml — the agent cannot send a message without explicit policy authorisation.

Rejected: HMAC-only inbound auth. Twilio HMAC keys are static and have appeared in misconfigured repositories at the rate of several per quarter in industry-wide credential leak reports; defence-in-depth with a short-lived capability token reduces blast radius by ≈ 3 orders of magnitude.

L6-D6 — Typed ChannelCapabilities + degradation tracking

LOCKED Capabilities are typed, not strings

Each ChannelConnector declares its ChannelCapabilities at construction. The struct is a #[non_exhaustive] set of typed flags and limits, not a HashMap<String, serde_json::Value>. v0.1 fields: max_text_bytes, supports_markdown, supports_html, supports_quote_reply, supports_threads, supports_reactions, supports_typing_indicators, supports_read_receipts, supports_edit, supports_delete, supports_attachments, max_attachment_bytes, supported_attachment_types, supports_voice_notes, supports_location, supports_buttons, supports_lists, supports_polls, has_24h_reengagement_window (WhatsApp), rate_limit: RateLimitProfile.

When the agent emits content the target channel cannot fully render, the iris-runtime degrades it according to a typed DegradationPolicy (strip markdown, inline attachment URLs, split long text, drop typing indicators silently) and emits an iris.capability_degraded { conversation, from_capability, to_capability } event so observability shows where degradation occurred. Agents reading the conversation log can adjust subsequent messages.

Rejected: capabilities as opaque strings or feature flags. Strings invite typos; feature flags don’t carry limits (e.g. max_attachment_bytes) and don’t version cleanly. The typed struct is more verbose but compiles, lints, and versions correctly — the trade is worth it.

L6-D7 — Public spec publication post-Phase-1

LOCKED Apache-2.0 publication after conformance green

After F-Sub-A … F-Sub-G ship, the conformance battery is green on ≥ 3 channels, and the trait surface has been stable for ≥ 30 days, iris-core + iris-conformance + the spec document are extracted to a standalone repository (broomva/agent-comms-contract, working name) published to crates.io and Cargo registry under Apache-2.0. The goals mirror Spec E’s publication play (L5-D8):

  1. Any messaging vendor (Twilio, Vonage, MessageBird, Sinch, Plivo) can target the contract — we become an aggregation surface, not a captive customer.
  2. Any agent runtime (LangGraph, LlamaIndex, AutoGen) can consume Iris connectors written against the published trait. Life is the reference implementation; downstream runtimes can fork.
  3. Per-channel adapters become a viable community-contribution surface gated by the conformance battery (mitigating the libpurple plugin-overload failure mode — see §9 concern C-7).

Rejected: keep the contract private as a Broomva moat. Six-month lead-time is real, but the structural moat is the substrate cluster integration (Anima identity, Lago events, Vigil semconv, Haima billing, Chronos windows) — not the trait itself. Owning the contract by being its publisher and reference implementation is worth more long-term than holding it private.

L6-D8 — Adapters are compiled-in Rust crates in v1

LOCKED Compiled-in crates with conformance battery (plugin daemon deferred)

In Phase 1, every channel adapter is a Rust crate (iris-whatsapp-openwa, iris-telegram, …) that implements ChannelConnector directly. Adapters are added to a release build by adding to Cargo.toml and rebuilding irisd. The trait surface is small enough that this is genuinely cheap; the cross-channel conformance battery (F-Sub-G) is the gate for any new adapter.

A plugin daemon alternative — in which adapters are separate processes (or WASM modules) that speak a wire protocol to irisd — is documented as Open Question O-1. The expected payoff (community-contributable adapters, language diversity, sandboxing safety) is real; the costs (wire-protocol versioning, ABI stability, performance overhead, deployment complexity, debugging complexity) are also real. The compiled-in path is the v1 choice because:

  • Phase 1 channels (WhatsApp OpenWA + WA Cloud + Telegram + Twilio SMS) are all maintained in-house and Rust SDK availability is good.
  • Compiled-in is dramatically simpler to debug and observe — one process, one stack trace, one Vigil span tree.
  • The libpurple lesson (community plugins fragment quality and security) is a real risk that the conformance battery alone doesn’t close.
  • Phase 2 can add a plugin-daemon mechanism without breaking the compiled-in path — it’s an additive change, not a swap.

Rejected for v1 (deferred to Phase 2): a libpurple-style plugin daemon model. Re-evaluated as part of O-1 after Phase 1 lands.

§4 Trait Surface — ChannelConnector and friends

This section presents the v0.1 trait surface as pseudo-Rust. No code is shipped by this spec; the Rust here is the design illustration that F-Sub-A turns into real crates.

§4.1 The ChannelConnector trait

// crates/iris/iris-core/src/connector.rs    (pseudo-Rust, design illustration)

use std::pin::Pin;
use std::sync::Arc;
use futures::Stream;

/// One channel adapter implements one ChannelConnector.
/// All adapters expose this exact surface; channel-specific concerns
/// live behind it (HMAC verification, native API calls, rate-limit handling).
pub trait ChannelConnector: Send + Sync + 'static {

    /// Identity of this connector instance, used in metrics + policy + Lago events.
    /// E.g. "whatsapp-openwa", "telegram", "twilio-sms-us1".
    fn channel_id(&self) -> &ChannelId;

    /// Declared capabilities of this channel (markdown, attachments, rate limits, &c.).
    /// Mostly static per channel, but may vary (e.g. WA Cloud business-account
    /// rate-limit tier).  Refreshed at startup; capability change emits an
    /// `iris.capability_degraded` event.
    fn capabilities(&self) -> &ChannelCapabilities;

    /// Trust regime under which this connector operates (Puppeting / Relay / Proxy).
    fn trust_mode(&self) -> TrustMode;

    /// Send an outbound message.  Returns the channel-native message id on success
    /// and a typed error on failure; transient failures retry per the connector's
    /// internal policy (capability-declared `rate_limit`).
    fn send<'a>(&'a self, msg: &'a Message)
        -> Pin Pin(&'a self, request: &'a RotationRequest)
        -> Pin Option<EngagementWindow> {
        None
    }
}

§4.3 TrustMode — the three trust regimes

// crates/iris/iris-core/src/trust.rs   (pseudo-Rust, design illustration)

/// Which identity model does this connector use?
#[non_exhaustive]
pub enum TrustMode {

    /// Puppeting: the bridge controls the remote-side identity directly.
    /// Example: a mautrix Telegram bridge that creates Matrix puppets for
    /// each Telegram user it sees.  The agent speaks AS the user on the
    /// other side. High consent burden — only legal with explicit user
    /// authorisation.
    Puppeting,

    /// Relay: the bridge speaks on behalf of users to a foreign network.
    /// Example: a Slack relay account that posts "carlos: hello" into a
    /// Discord channel.  The agent has its own foreign-network identity;
    /// users are mentioned by name, not by identity.  Lower consent burden;
    /// the foreign network sees one identity (the relay).
    Relay,

    /// Proxy: the bridge mediates without claiming any identity.
    /// Example: Twilio SMS — the agent has its own phone number; users
    /// have theirs; nobody is puppeting anybody.  Default + lowest-friction.
    Proxy,
}

Per-channel default trust modes in v0.1: WhatsApp OpenWA = Puppeting (the bridge logs into a user’s WA account — this is the bridge’s risk surface). WhatsApp Cloud = Proxy. Telegram = Proxy (bot account) or Puppeting (MTProto user account). Signal = Proxy (signal-cli bot). Slack = Proxy (bot user). Discord = Proxy (bot account). Matrix = configurable. iMessage = Puppeting (bridge logs in as the user via Apple ID). Twilio SMS = Proxy. Web = Proxy.

Puppeting connectors are gated by an additional iris.<channel>.puppeting.consent policy that must be explicitly enabled per tenant; the default deny prevents accidental puppeting.

§7 Composition with Shipped Substrates

§7.1 Anima (Spec D)

Iris consumes Anima for all identity concerns. irisd holds an Arc<dyn AnimaCustody> resolved at startup from the tenant’s Anima configuration (InProcessAnima in dev, VaultTransitAnima or SomaCustody in production).

  • Identity bootstrap (L6-D4) derives an ephemeral EcdsaP256Identity via HKDF and emits an iris.identity_bootstrapped event.
  • Permanent-DID upgrade arrives as an anima.identity_rotated event in the Anima journal; Iris replays the rotation chain to resolve historical conversations.
  • JWS / digest signing for outbound messages that carry a verifiable agent identity claim uses Anima’s sign_jws / sign_digest directly. Iris never holds key material.

§7.2 Inference (Spec E)

Iris consumes Inference for per-channel, per-conversation compute routing. The InferenceRouter’s RoutingHint gets extended (or extended via a side-channel until F-Sub-E lands) with channel metadata (channel_id, workload: ConversationReply, optional latency_target_ms). Channels with tight latency requirements (SMS, voice IVR — out of scope) route to small-model backends; long-form async channels (email, Matrix room with no urgency) route to large-model backends.

Inference’s close-code vocabulary (CloseCode::ToolAwait, BackendUnavailable, AnimaInvalidated) maps onto Iris’s outbound-send failure handling. An Inference failure that blocks outbound is reported back as a typed iris.message_failed { reason: inference_*, … } event so an operator dashboard can disambiguate channel failures from inference failures.

§7.3 Lago

Lago is the durability substrate (L6-D2). Every Iris event is content-addressed, journal-appended, and replayable. The Lago tag-walk pattern that Anima uses for rotation chains is the same one Iris uses for engagement-window state queries; the queries land in lago-knowledge.

lago replay --tree is extended to surface conversation history alongside agent decision events, completing the workflow-tick closure pattern documented in the workspace. The same authoring-agents adapter that arcand uses for workflow events is the model for iris-runtime.

§7.4 Chronos

Chronos owns three Iris-relevant timer kinds:

  1. Engagement-window timers (WhatsApp 24h). When an inbound WhatsApp message arrives, Iris arms a Chronos 24h timer keyed by ConversationRef. On expiry, Chronos fires an event that Iris consumes to close the window (transitioning outbound to template-only).
  2. Idle conversation reaping (default 24h after last activity, configurable). Frees per-conversation locks.
  3. Rate-limit window timers for connectors that need explicit windows (e.g. Twilio 1 msg/sec, WA Cloud per-template quotas). These are typically internal to connectors; surfaced via Chronos when global coordination across irisd instances is needed (Phase 2+).

§7.5 Vigil

Vigil hosts the Iris-specific span kinds and metric series declared in F-Sub-F. OTel GenAI semantic conventions extend cleanly to messaging (the messaging.* namespace is well-established in OpenTelemetry); Iris adopts the standard messaging.system, messaging.destination.name, messaging.operation attributes plus the Life-specific extensions iris.channel_id, iris.conversation_id, iris.trust_mode, iris.capability_degraded.

§7.6 Haima

Haima receives per-message billing ticks. Outbound message paths that have a per-message cost (Twilio SMS at ~0.0075 USD per US-domestic message, WhatsApp Cloud per-conversation fees) fire a Haima TaskBilled event with the channel-specific cost loaded from the connector’s capability profile. Inbound paths typically have no per-message cost; they fire only on the lifegw rate-limit budget surface.

§7.7 Soma

No direct composition surface. irisd does not call soma. The relationship is mediated through Anima (which may consult SomaCustody if that’s the configured backend). Iris’s threat model does not place soma in its trust path.

§8 Strategic Positioning — POSIX of Agent Messaging

Spec E framed Inference as the POSIX of agent silicon — own the runtime contract, hardware vendors compete underneath. Iris is the same play at the messaging layer: own the canonical conversation contract, channels compete underneath.

§8.1 The leverage

  1. Channel vendors aggregate around the contract. Twilio, Vonage, MessageBird, Sinch, Plivo, BIRD/Twilio Conversations, Meta’s WA Cloud, Telegram, Discord all benefit from a runtime that consumes them on equal footing. Lock-in is reduced; switching cost is reduced; the contract owner sits above the substitution surface.
  2. Agent runtimes downstream consume Iris connectors. Any runtime that wants to send/receive on twenty channels can either reimplement Iris or consume iris-core-conforming connectors. The leverage flows toward the contract publisher.
  3. Community-contributed adapters become feasible once the conformance battery (F-Sub-G) gates entry. Iris adopts the libpurple shape but mitigates the libpurple failure mode (quality drift) via conformance.
  4. Tenant deployments accelerate. The fifteen near-duplicate integrations forecast across five tenants in twelve weeks (see §1.1) collapse to one substrate plus tenant-side configuration. The marginal cost of channel N+1 approaches zero.

§8.2 What we’re not betting on

We are not betting on Iris becoming the universal messaging abstraction across all of computing. We are betting on it becoming the universal agent-side messaging abstraction — i.e. the bridge between agent runtimes and channels — which is a narrower surface where the existing prior art (libpurple, mautrix, Bot Framework, Twilio Conversations, OpenClaw) has already converged on the eight invariants. Iris’s job is to ship the convergence, not to invent it.

§8.3 Adjacency to the published Spec E contract

Spec E’s agent-loop-compute-contract publication and Spec F’s agent-comms-contract publication form a pair. Together they describe the agent runtime’s two largest external interfaces: compute (silicon) and communication (channels). The pair narrative — "the two contracts every agent runtime needs" — is materially stronger than either alone for the standardization play. Phase 2 may extract an umbrella spec (agent-runtime-contracts) linking both; that’s out of scope for v1.

§9 Concerns & Mitigations

# Concern Likelihood / Impact Mitigation
C-1 OpenWA WhatsApp Web automation ToS risk. OpenWA-class adapters automate WhatsApp Web sessions; this is in tension with WhatsApp’s Terms of Service for personal accounts and has historically resulted in account bans. High / High Ship both OpenWA (F-Sub-B) and WA Cloud (F-Sub-H) in v1. The Cloud API is ToS-blessed; OpenWA is opt-in per tenant with a documented risk-acknowledgment policy gate (iris.whatsapp.openwa.acknowledge_tos_risk) and a default-deny stance. Tenants who choose OpenWA accept the operational risk; tenants on regulated business workloads default to WA Cloud. Iris connectors are interchangeable from the agent’s perspective.
C-2 SMS spoofing during identity bootstrap. An attacker who can spoof inbound SMS from a target phone number could trigger ephemeral-DID creation for a number they don’t control, then convince the agent to act on the spoofed identity. Med / High The ephemeral-DID path (L6-D4) does not grant the agent the right to take any irreversible action (financial transfer, account creation, identity assertion) on the bootstrapped DID’s behalf. Such actions require an upgraded permanent DID via the WebCryptoAnima passkey + phone-OTP-proof flow (Figure 5.3, bottom row), at which point the proof binds the phone number to a key the attacker cannot forge. Until then, the DID is treated as provisional and the policy gates require explicit per-action authorisation.
C-3 Webhook authentication sprawl. Each channel has its own HMAC scheme, its own signing secret, its own header conventions. A mistake in any one of them is a credential leak surface; collectively they’re an attack surface that grows linearly with channel count. Med / Med Double-auth pattern (L6-D5): channel-native HMAC verification + Tier-Service capability token, both required. A leak in either alone is insufficient. Plus per-channel adapter HMAC verifiers are factored into iris-runtime::hmac so the verification path is testable and shared across adapters. F-Sub-G conformance battery includes HMAC-rejection tests.
C-4 Session affinity / phone-bound resolver. Inbound messages need to land at the same irisd instance that holds the per-conversation lock; horizontal scaling of irisd requires routing. Med / Med irisd instances form a consistent-hash ring keyed by ConversationRef. lifegw includes a session-affinity router (a small extension to existing tonic UDS routing) that forwards inbound to the right instance. Falls back to any-instance + lock-acquire-via-soma-coordinator if the affinity router is unhealthy. Per-conversation lock is then held via a soma-coordinated semaphore until idle reap. Phase 2 work; v1 ships single-instance irisd.
C-5 Rate limits. Channels enforce per-account and per-recipient rate limits (Twilio 1 msg/sec/number, WA Cloud per-quality-rating tier, Telegram 30 msg/sec/bot, etc.). Exceeding them produces deliveries silently dropped or accounts suspended. High / Med Per-channel RateLimitProfile in ChannelCapabilities declares limits. iris-runtime consumes these via a token-bucket per (channel, destination); excess fires a typed RateLimited { retry_after_ms } error that the agent can choose to back-off-and-retry or surface. lifegw also enforces a global per-tenant outbound rate limit as a second safety net (configured in .control/policy.yaml).
C-6 Control gate enforcement. Outbound messages can have material real-world consequence (financial, legal, reputational). Without explicit gating, an agent could send messages at scale before a human notices. Low / Very High Every per-channel outbound is gated by a iris.<channel>.outbound.send policy in .control/policy.yaml. Bulk outbound (multiple recipients in one tick, or N> threshold within a window) is gated by a separate iris.<channel>.outbound.bulk gate that defaults to require-approval. Puppeting connectors additionally require iris.<channel>.puppeting.consent. The control-metalayer harness reasoning enforces these (CLAUDE.md P2 Control Gate).
C-7 Plugin overload — the libpurple lesson. Adding more channels makes the substrate harder to maintain, less reliable, less secure as community-contributed adapters of varying quality accumulate. Med / High v1 ships compiled-in Rust crates only (L6-D8) with a conformance battery (F-Sub-G) gating any new adapter. Open Question O-1 evaluates a Phase 2 plugin daemon model with explicit conformance + sandboxing requirements. The libpurple failure mode — community plugins of varying quality entering production unaudited — is specifically what F-Sub-G prevents.
C-8 Schema drift — the Bot Framework lesson. Canonical message schemas accumulate channel-specific quirks; over years they drift and fragment. Med / Med Channel-specific data lives in Message::channel_data: Option<serde_json::Value> (Bot Framework channelData pattern). The canonical schema itself is #[non_exhaustive] at every union; additive evolution is supported, breaking change requires a major version bump. Cross-channel conformance battery (F-Sub-G) tests the canonical schema against all adapters every CI run.
C-9 iMessage adapter operational cost. iMessage has no official server-side API; bridges (Beeper, mautrix-imessage, JMP.chat) require a Mac mini physically logged into an Apple ID. This is hardware + operational overhead, not just code. Low / Low (only if iMessage adopted) iris-imessage is intentionally last in the adapter priority list. Document the operational requirement (a tenant-provided Mac mini); offer no v1 deployment of iris-imessage from Iris itself. The trait surface is designed to be implementable by such a bridge but the bridge ships separately.
C-10 PII in Lago journal. Inbound message bodies frequently contain PII (names, addresses, account numbers, health information). Storing them indefinitely in Lago creates a data-retention concern. Med / High Iris messages in Lago are scoped to the participant’s Anima DID; PII deletion is implemented via anima.identity_revoked + a Lago tombstone pass (Phase 2 work; not v1 blocker). For v1, Iris ships with per-tenant configurable retention (default 90 days) implemented as a Chronos timer + a Lago purge pass that hashes message bodies after retention. Tenant deployments with regulated workloads can configure shorter retention.
Ten concerns plus mitigations. C-1 (ToS) and C-2 (spoofing) carry the highest combined likelihood × impact and have first-class mitigations baked into the locked decisions.

§10 Open Questions

Open questions are deliberately deferred — either because they don’t affect v1 trait shape, because they need empirical data from F-Sub-G conformance results, or because they require a decision the spec author cannot make unilaterally.

O-1 — Compiled-in Rust crates vs plugin-daemon adapters (most consequential)

L6-D8 locks v1 to compiled-in Rust crates. Phase 2 may add a plugin-daemon model (libpurple-style separate processes, or WASM components speaking a wire protocol to irisd). The decision matrix:

Dimension Compiled-in Rust (v1) Plugin daemon (libpurple-style, Phase 2)
Community contribution velocity Lower — contributors must clone the workspace and submit Rust PRs. Higher — adapters can be in any language, published independently.
Sandboxing safety None — adapter shares irisd address space and crashes the daemon on panic. Strong — adapter crash is isolated; WASM impl gets capability-based sandboxing.
Binary size Larger irisd binary; adapters not used are still linked unless feature-gated. Smaller core; adapters loaded on demand.
Deployment complexity One binary, one process; trivial. N+1 processes; supervisor; IPC; observability tree spans multiple processes.
Performance overhead Zero — in-process function call. Wire-protocol overhead per call (likely sub-millisecond, but non-zero).
Debugging Single stack trace, single span tree, single core dump. Distributed stack trace; cross-process span correlation required.
ABI stability requirement Source-level compatibility within a major version. Wire-protocol versioning; semver of the wire is harder than semver of source.

Decision criteria for Phase 2: if F-Sub-G conformance proves the trait surface is stable after 60 days of v1 production and ≥ 3 tenants want custom channel adapters that can’t reasonably ship as Rust crates, pursue the plugin daemon. Otherwise stay compiled-in. The trait shape is designed to be wire-protocol-implementable from day one (every type is serializable, every method is async or returns a future), so the Phase 2 add is genuinely additive.

O-2 — Spec letter reconciliation (very consequential, procedural)

Two specs claim the letter F (this Iris spec and the in-flight subscription-auth spec at 2026-05-11-spec-f-subscription-auth-tier-1.md). Per §0.3 the default is to rename the prior document to Spec H once Iris F-Sub-A merges; the alternative is to rename Iris to the next-open letter. Reconciliation must happen before any of F-Sub-A’s artifacts ship to main. This is a notation question, not a substrate question, but it’s consequential because the letter propagates into Linear tickets, branch names, commit messages, and long-lived URLs.

O-3 — Group conversations and channel-native group semantics (consequential)

Channels disagree about group conversations. WhatsApp groups have administrators and join-by-link semantics; Telegram groups have a similar but distinct model; Signal groups are end-to-end encrypted with a different administrative shape; Slack channels have an org-wide namespace; Discord channels live inside guilds. The canonical ConversationRef::Group kind in v0.1 is intentionally underspecified — sufficient for routing and ordering but not for cross-channel group-management UX. Phase 2 needs a typed GroupCapabilities sibling of ChannelCapabilities. For v1, group conversations work but group management (add member, remove member, change admin) is delegated to native channel APIs via Message::channel_data passthrough.

O-4 — Multi-instance irisd coordination (operational, deferred)

v1 ships single-instance irisd per tenant. Multi-instance horizontal scaling requires the consistent-hash router (concern C-4) and a cross-instance per-conversation lock (probably via soma coordination or a Lago-backed distributed lock with a Chronos TTL fallback). Both are designed for but not implemented in v1; deferral lets v1 ship and operational experience inform the design.

O-5 — Inference channel-awareness (routing, post-Phase-1)

The RoutingHint in Spec E v0.1 does not carry channel metadata. A small extension — adding channel_id: Option<ChannelId> and latency_target_ms: Option<u32> to RoutingHint — would let Inference route, e.g., SMS replies to low-TTFT backends and Matrix long-form responses to higher-throughput backends. Coordinate with Spec E E-Sub-E (inference-autonomic) post-F-Sub-A.

O-6 — Voice and video channels (scope boundary)

Voice calls (Twilio Voice, WhatsApp voice notes, Signal voice messages), video calls (Whereby, Daily, Matrix VoIP), and presence indicators (Slack online status, Discord typing) are explicitly out of scope for v1 (§11). The trait surface is designed to be voice-extensible (VoiceConnector: ChannelConnector sub-trait is feasible) but adding voice would re-open every locked decision around serialization, capabilities, and trust modes. Phase 2+ topic.

O-7 — PII / retention (regulatory)

Default retention of 90 days (concern C-10) is a guess, not a derived constraint. Different tenants have different regulatory regimes (HIPAA in healthcare, GLBA in financial, GDPR in EU, LGPD in Brazil, …); Iris should ship configurable retention per tenant but the workspace-level default needs review by counsel before any production tenant onboarding. Documented as a v1 limitation; reviewed in the v1.1 cycle.

O-8 — Engagement-window semantics across channels other than WhatsApp (modeling)

WhatsApp’s 24-hour customer-care window is the most prominent example, but Telegram bot accounts have their own re-engagement restrictions, Slack has Connect-channel external-message limits, and iMessage has read-status implications. Should EngagementWindow generalise to a typed sum across channel-specific window kinds, or stay WhatsApp-flavoured? Decision blocked on F-Sub-C (Telegram) implementation experience.

§11 Out of Scope (Phase 2+)

  • Voice / audio channels. Twilio Voice, WhatsApp voice notes, Signal voice notes, telephony in general. The trait surface is voice-extensible; Phase 2 may add VoiceConnector: ChannelConnector.
  • Video calls. Daily, Whereby, Jitsi, Matrix VoIP, Google Meet, Zoom integration. Out of scope by an order of magnitude — video calls are real-time, stream-based, and a different substrate shape entirely.
  • Real-time presence indicators. Slack online status, Discord typing indicators, WhatsApp last-seen. Different cadence (high- frequency, low-information) from messaging; deserves its own substrate or sub-substrate (provisional name: Aura).
  • Advanced group-call features. Multi-party voice/video, meeting recording, transcription, screen-sharing, breakout rooms. All compose with the planned Vigil + Mnemo + Aegis stack and need their own design.
  • Cross-channel forwarding. "Inbound on WhatsApp, outbound forwarded to Slack" — an interesting feature but requires careful trust-mode reasoning (the forwarded message’s from on the receiving channel is the agent, not the original sender; the trust regimes don’t compose cleanly). Documented; deferred.
  • AI-generated multi-modal response rendering per-channel quirks. Channel-specific best-format detection ("this is best rendered as a Slack-blocks layout", "this should be a Telegram inline keyboard", "this is a WhatsApp template") is a separate optimisation surface that consumes Iris but lives upstream in the agent.
